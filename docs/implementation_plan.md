# Implementation Plan

Each stage ends with something runnable and testable. We finish and verify one stage before starting the next.
Status legend: `[ ]` not started, `[~]` in progress, `[x]` done.

## Decisions

| Topic | Decision | Why |
|---|---|---|
| LLM | Azure OpenAI (`gpt-5-nano`) via the `openai` SDK's `AzureOpenAI` client, behind a thin `llm_service` so the provider can be swapped | Single integration point; endpoint, API version and deployment name come from `.env` |
| Secrets | `GENAI_PLATFORM_API_KEY` and other secrets live in `backend/.env` (git-ignored) | Never in code or frontend |
| Databases | PostgreSQL first (external connections). MySQL added later as a dialect extension. **Decided at the end of Stage 10 to leave MySQL out of this version** (see 10c) | SQLAlchemy + SQLGlot both support it, so this is mostly config and tests |
| Uploaded data | Imported into a per-workspace SQLite file | Zero-install for dev; the same pipeline then runs on it as on external DBs |
| Auth | Workspace/session ID early on; real authentication in the hardening stage | Keeps early stages simple without hard-coding unsafe assumptions |
| RAG / agents | Deferred. The workflow is plain Python services; vector RAG only if docs warrant it | README says neither is mandatory |
| Frontend timing | Backend stages are tested via pytest and FastAPI `/docs`; React comes after the core pipeline works | Pipeline correctness matters more than UI early on |

## Stages

### Stage 0: Project scaffolding `[x]`
- Create the folder structure, `requirements.txt`, `.env.example`, `.gitignore`, and `git init`.
- FastAPI app with `/health`, config loading from `.env`, and pytest set up.
- **Done when:** `uvicorn app.main:app` runs, `/health` returns OK, and `pytest` passes.

### Stage 1: Sample data and data sources `[x]`
- Create a sample business DB (customers, products, orders, plus payments/regions for harder joins) with seed data and edge cases.
- CSV and Excel upload: validate files, enforce size/row limits, sanitize table and column names, import into per-workspace SQLite, and return a preview.
- Excel sheet selection.
- Data source registry (list, delete).
- **Done when:** a CSV and a multi-sheet Excel file can be uploaded through `/docs`, and the tables appear in the registry.

### Stage 2: Schema extraction and relationships `[x]`
- SQLAlchemy Inspector extracts tables, columns, types, PKs, and FKs.
- Relationship service: FK-based join graph, junction-table detection, and a join-path finder.
- Uploaded tables have no FKs, so we suggest relationships (by column name and type) for the user to confirm; nothing is guessed silently.
- **Done when:** `GET /schema` returns tables and relationships, and the join-path finder passes unit tests on the sample DB.

### Stage 3: Schema linking and SQL generation `[x]`
- Schema linking selects relevant tables and columns for a question (keyword matching first, embeddings later if needed).
- `llm_service` wraps Azure OpenAI.
- Prompt builder includes the relevant schema, join paths, SQL dialect, and conversation context.
- SQL generation returns SQL plus a plain-language explanation as structured output.
- **Done when:** questions against the sample DB produce sensible SQL (not yet executed).

### Stage 4: Validation and safe execution (security-critical) `[x]`
- SQLGlot validator: parse, allow only a single SELECT, check tables and columns against the schema, reject DDL/DML and system schemas, and allowlist constructs.
- Executor: read-only connection (SQLite `mode=ro`, Postgres read-only role/transaction), statement timeout, and row cap.
- Controlled correction loop: sanitized error → LLM → full revalidation, with a max retry count.
- **Done when:** unsafe SQL tests are all rejected (DROP, multi-statement, unknown column, and so on), and valid queries run with limits applied.
- **Built:** two independent layers. The validator (`sql_validation.py`) checks structure, an allowlist of constructs and functions, and tables/columns with proper scoping. The executor (`query_execution.py`) opens SQLite read-only, installs a SQLite authorizer (SELECT, known tables and safe functions only), enforces a time limit and row cap, and lowers SQLite's value-size limit. Endpoints: `/api/sql/validate`, `/api/sql/execute` (always validates first), `/api/sql/query` (question → checked result). Config: `SQL_MAX_ATTEMPTS`, `BLOCKED_COLUMNS`, `QUERY_TIMEOUT_SECONDS`, `QUERY_MAX_ROWS`.
- **Fixed during review:** a CTE named like a table (`WITH x AS (SELECT * FROM x)`) could hide a real table lookup from the unknown/blocked-table check. Table references are now resolved by scope.

### Stage 5: Analyst workflow and chat API `[x]`
- `analyst_workflow` orchestrates: question → ambiguity check → link → generate → validate → execute. It wraps the existing `query_pipeline.run_question`.
- Ambiguity detection: return a clarification question with options.
- Conversation manager for follow-ups; every follow-up is revalidated.
- `POST /api/chat/query` returns SQL, explanation, validation status, and results.
- **Done when:** the README scenarios D and E (ambiguity and follow-ups) work end to end via the API.
- **Built:** `ambiguity_service.py` has two paths: a deterministic check (several equally short join paths → ask which relationship, no LLM call) and a focused LLM check that asks only when an undefined measure would change the result. An unusable reply from the check counts as "not ambiguous", so it can never block a question. A message that answers a clarification skips the check. Conversations (`conversation_service.py`) store questions, SQL and result column names/row counts, never result rows; the last 6 answered or clarified turns go into the prompt, failed turns do not. Schema linking uses earlier questions and pins the previous answer's tables so "now only the top five" still finds its tables. Endpoints: `POST /api/chat/query` (optional `conversation_id`), `GET/DELETE /api/chat/conversations[/{id}]`. Config: `AMBIGUITY_CHECK` (default on).
- **Live results (gpt-5-nano):** the 3 vague questions tried all asked with 3 schema-grounded options; the 5 clear questions ran with no needless questions; scenarios D and E completed end to end.
- **Fixed during review:** conversations created in the same second could be listed in the wrong order (second-resolution timestamps with a random tie-breaker). Timestamps now have microsecond resolution plus insertion order as the tie-break.
- **Known limits, tracked below:** (1) latency: a chat message makes two sequential LLM calls (ambiguity check, then generation), about 10 s in total with this model. Options: run them concurrently, or skip the check for clearly specific questions (Stage 10; Stage 7's UI should show progress). (2) "Compare it with 2024" produced valid SQL that lists all 24 year-months with one column zero per row instead of lining months up side by side. That is model quality, so it goes into the Stage 10 evaluation set rather than being patched with prompt tweaks.

### Stage 6: Result analysis and visualization `[x]`
- Pandas profiling: row count, column types, min/max, trends.
- Chart selection rules (bar/line/pie/scatter/table/KPI) that output a chart spec.
- LLM summary grounded only in the returned data.
- **Done when:** the chat response includes a chart spec and a summary, and chart selection is tested.
- **Built:** `result_analysis.py` profiles a result (kinds: numeric, temporal, categorical, text, boolean, identifier; statistics; computed "facts" such as highest, lowest, share of total, change over time). `visualization.py` picks KPI, bar, line, pie, scatter or table by rule, honours a requested type ("as a pie chart") when the data supports it and otherwise says why not in `notes`, pivots multi-series data, caps large results, and lists feasible `alternatives` so the UI can offer a switch. `result_summary.py` asks the LLM for a summary from the facts and rows, then **checks every figure in it against the data**: an ungrounded figure (including "9 million" or "5%") gets one correction attempt and then a deterministic template summary replaces it, so an invented number is never returned. Chat responses now carry `analysis` (`profile`, `chart`, `summary`, `summary_source`). Endpoints: `POST /api/analytics/chart` and `POST /api/analytics/summary` work on a result the client already holds, so the UI can switch chart types instantly and fetch the summary separately (`include_summary=false` on chat). Summaries are stored on conversation turns. Config: `SUMMARY_MAX_ROWS` (default 50; 0 sends only computed facts, no row data, to the LLM).
- **Live results (gpt-5-nano):** KPI, bar, line and pie were chosen correctly for four question types and every summary passed the grounding check.
- **Fixed during review:** (1) infinity values were cleaned after the null filter and turned a numeric column into a categorical one; (2) data labels embedded in the computed facts could inject lines into the summary prompt, so labels are now flattened; (3) the grounding check let "9 million" and "5%" through via the small-number exemption, which no longer applies to numbers with a magnitude word or percent sign; (4) the model wrote numbers in quotation marks because the prompt said "quote"; (5) a share question returning both a count and a share column got a bar instead of a pie; (6) pivoted charts were titled with every series name; (7) key columns such as a repeated `customer_id` were treated as measures. Existing registries are upgraded in place (`turns.summary` column) by `init_registry`.
- **Known limits:** the summary is a third LLM call (about 5 s), so the Stage 7 UI should request chat with `include_summary=false`, draw the chart and table first, then call `/api/analytics/summary`. The grounding check cannot catch a wrong claim built from correct numbers (for example calling a decline a "growth"), so qualitative statements stay as trustworthy as the model; the rules forbid causes and predictions but are not mechanically checked.

### Stage 8: PostgreSQL connection and schema explorer `[x]`
- Connect to an external PostgreSQL DB (test connection, credentials stored backend-side only, host allowlist). Add the connection form to the Data page (a disabled placeholder card is there now) and a `POST /api/database/connect` endpoint.
- Postgres read-only enforcement and dialect handling. The Stage 4 executor is SQLite-specific; add a Postgres executor behind the same `execute_query` interface (read-only role, `SET TRANSACTION READ ONLY`, `statement_timeout`, schema allowlist) and review the validator's function/construct allowlists for the Postgres dialect (`SAFE_*` sets in `sql_validation.py`; block `pg_sleep`, `pg_read_file`, `COPY`, etc.).
- Visual schema explorer (tables, keys, relationship diagram).
- **Done when:** the pipeline works on a real Postgres database, and the explorer renders.
- **Built:** a `Connector` abstraction (`connectors.py`: `engine()`, `execute()`, `cache_key()`, `dialect`) that SQLite files and PostgreSQL servers implement, so schema extraction, relationships, linking, validation and execution no longer know about file paths. **PostgreSQL safety, in layers:** (1) the validator, now **dialect-aware** (`sql_allowlist.py`: per-dialect function and construct allowlists derived from sample calls, plus a check that mixed-case names are double-quoted exactly as in the schema); (2) a **read-only transaction on every connection**, set per transaction so it works behind poolers, together with a server-side `statement_timeout`, `lock_timeout`, UTC time zone and a `search_path` limited to the chosen schema, applied with one real `set_config` query so the mode cannot be switched back inside the transaction; (3) account checks at connect time: **superusers are refused**, and write privileges, powerful built-in roles and unencrypted remote traffic produce warnings. **Connecting:** `POST /api/database/test` and `/connect`, `POST /api/datasources/{id}/refresh`; the **host must be on `ALLOWED_DB_HOSTS`** (default: this machine only; link-local/metadata addresses are always refused), passwords are **encrypted at rest** (Fernet, key from `CREDENTIALS_KEY` or a generated `data/credentials.key`) and never returned, driver errors are translated into plain messages with the password scrubbed, and request-validation errors no longer echo submitted values. A database outage is reported as 503 everywhere. **Frontend:** connection form (test, connect, warnings, password never stored in the browser), PostgreSQL cards with host/database, Refresh schema and Disconnect, and an interactive **relationship diagram** on the Schema page (tables as boxes with key columns first, N/1 markers, hover/focus highlights, keyboard selectable). **Dev tooling:** `scripts/dev_postgres.py` starts a real embedded PostgreSQL 16 with the sample data and a read-only `analyst` role, with no installation or admin rights (`requirements-dev.txt`); the PostgreSQL tests use the same server, or your own via `TEST_POSTGRES_URL`, and are skipped if neither is available.
- **Verified against real PostgreSQL 16.15** (not a mock): 39 connector tests including the read-only guarantee proven directly through the engine for an account that *can* write, 34 API tests, 145 validator tests across both dialects; 8 live questions answered correctly by `gpt-5-nano` in PostgreSQL syntax (`date_trunc`, `DATE` literals, date subtraction); and the full flow in a real browser (host-not-allowed, superuser and wrong-database refusals, test, connect, diagram, a live question that became a line chart, disconnect).
- **Fixed during review:** (1) the host check refused `localhost` itself, because Python calls IPv6 `::1` "reserved"; (2) `SET TRANSACTION READ WRITE` still worked right after the read-only setup, since PostgreSQL only locks the mode after the first real query (now closed); (3) errors raised while connecting carry no SQLSTATE, so a mistyped database name got a generic message (the server's wording is now recognised too); (4) a correctly quoted mixed-case name was rejected because SQLGlot lower-cased the schema (PostgreSQL names are now given exactly); (5) `date_trunc` results carried the server's time zone offset, which would have shifted month boundaries and broken date detection (UTC, midnights shown as plain dates); (6) the diagram's tooltip read "many-to_one".
- **Known limits:** views and materialized views are not listed (only tables); only one schema per connection; blocked columns on PostgreSQL rely on the validator (PostgreSQL has no per-statement authorizer), so also use column-level `GRANT`s; the allowlist is checked against the name you type and then the driver resolves it again, so pinning the resolved address (`hostaddr`) is a Stage 10 hardening item; value hints on tables over 200k rows are sampled; the embedded dev server keeps running if its window is closed instead of pressing Ctrl+C (running the script again reuses it).

### Stage 9: Query history and business context `[x]`
- Query history (questions, SQL, status, retained results).
- Upload and index business definitions and data dictionaries; start with simple retrieval and add vector search only if needed.
- User-defined relationships and metrics are injected into prompts.
- **Done when:** a question using a defined term like "revenue" follows the supplied definition.
- **Built:** **Business definitions** (`context_service.py`, `/api/context/{datasource_id}`): four kinds per data source and workspace: *metric* (name, other names, meaning, optional SQL formula), *term*, *table note* and *column note*. A formula is checked when saved (it must parse, be one expression with no subquery, use only allowlisted functions for the dialect and only columns that exist), so a typo is caught immediately. Retrieval is deliberately simple and lexical (no vectors): a definition applies when its name or another name appears in the question or the recent conversation, more specific matches first, capped at 8 definitions / 2,400 characters; **a definition that names another definition brings it along** ("best-performing product = highest Revenue" also supplies Revenue's formula), table and column notes appear next to the schema they describe. The selected definitions go into the SQL prompt (new rule: use them exactly, never at the cost of the safety rules) and into the clarification check (a defined term is never ambiguous). Answers report `definitions_used`, and the UI shows "Followed your definition of Revenue". **Import** of .csv, .json, .md or .txt glossaries (preview first, then keep-or-replace), plus example definitions for the sample database. **Query history** (`/api/history`): search over question, SQL and summary, status filter, paging, delete one or clear all, a retention period (`HISTORY_RETENTION_DAYS`, default 90, applied at start-up and whenever a question is saved), and *optional* retained results: result rows are sensitive, so they are kept only if `HISTORY_RETAIN_ROWS` is above 0 (then at most that many rows, and never more than 2 MB, per answer). **Frontend:** a History page (search, status chips, SQL, Ask again, Open conversation, Run SQL again or Show saved results, delete, clear, a plain statement of what is kept) and a Definitions page (grouped list, add/edit with the server's reasons, import with preview, examples).
- **Verified:** 653 backend tests (new: 40 for definitions, 19 for prompts and chat, 29 for history and retention, including isolation between workspaces, LIKE-wildcard literals, expired rows, cascade on deleting a data source, and a hostile definition that cannot make unsafe SQL pass validation) and 213 frontend tests (new pages plus kept-rows, hand-off from History and definition chips). Live with `gpt-5-nano`: with the example definitions, "What is the total revenue?" returned the completed-orders figure in 5 of 5 repeated runs (166,670.84, not the all-orders total), and "Show me the best-performing product" went from a clarification (see Stage 5) to an answer that matches the reference product. Browser run: empty state, examples, a rejected formula with its reason, edit, CSV import preview and import, a live question with the definition chip, History search / re-run / ask again / open / delete / clear, and a phone-width check (no horizontal overflow).
- **Fixed during review:** (1) a markdown glossary line with `(also: ...)` was split at the wrong place, so the other names were lost; (2) a definition that refers to another ("as defined for Revenue") did not bring that one along, and the model improvised the missing formula from the `payments` table (found by the live run, fixed with tests first); (3) `<h4>` headings had browser margins that spread definition cards apart; (4) five navigation tabs were tight at phone width.
- **Known limits:** retrieval is by words, not meaning, so "turnover" works only if it is listed as another name (vector search is still deferred until a real need shows up); only a definition's own name counts as a reference to another definition; kept rows are the *first N rows*, not the whole result; definitions and history belong to a workspace, not a user, until Stage 10 adds authentication; the formula of a metric guides the model but is not substituted into the SQL, so the model can still ignore it (validation guards safety, not meaning); one answer can still list an incidental extra table in its chips.

### Stage 10: Hardening, evaluation `[x]` (MySQL left out)
Split into three parts, each ending with its own review: **10a security `[x]`**, **10b speed and evaluation `[x]`**, **10c documentation and database limits `[x]`**. MySQL, originally part of 10c, was left out.

#### 10a: Security `[x]`
- Authentication and per-user data isolation, rate limits (the LLM-backed endpoints are the costly ones), and log redaction.
- Make `BLOCKED_COLUMNS` per data source instead of one global setting.
- Pin the resolved address when connecting (`hostaddr`).
- **Built:** **Accounts** (`AUTH_MODE=accounts`, the default): register and log in with a username and password; passwords are salted **scrypt** hashes (N=2^15, parameters stored in the hash, absurd stored parameters refused), sessions are random bearer tokens of which only the SHA-256 is stored, expire after `SESSION_DAYS` of non-use and end on logout; changing a password ends the other sessions. Wrong-username and wrong-password answers are identical and take the same time (a dummy hash is checked for unknown users); repeated failures lock a username and, separately, a network address out (`LOGIN_MAX_FAILURES`, `LOGIN_MAX_FAILURES_PER_IP`, `LOGIN_LOCKOUT_MINUTES`); registration can be closed (`ALLOW_REGISTRATION`) and is rate-limited per address. A person's workspace is their user id, and **every endpoint gets its identity from one dependency** (`get_workspace_id`), so a test enumerates the OpenAPI paths and fails if any `/api` route answers without a login. In accounts mode the old `X-Workspace-Id` header is ignored, since it proves nothing; `AUTH_MODE=none` keeps it for one person on their own machine. **Rate limits:** per person per minute, and a lower shared limit for the four model-backed endpoints, refused before the model is called (`RATE_LIMIT_PER_MINUTE`, `RATE_LIMIT_LLM_PER_MINUTE`). **Security headers** on every response (`no-store` and a locked-down CSP on `/api`, no sniffing, no framing). **Log redaction** applied when a record is created, so it covers every logger, uvicorn's access log (query strings, where search terms land) and logged tracebacks: bearer tokens, `password=`/`api_key=` pairs, passwords in connection URLs, and the configured keys. **Blocked columns per data source and workspace** (`/api/datasources/{id}/blocked-columns`): merged with the administrator's `BLOCKED_COLUMNS` (shown as locked, never removable) and enforced by the validator and database layer as before, and now also **hidden from the schema the model sees, from value hints and from table previews** (a blocked table cannot be previewed); the value-hint cache is keyed by what is visible so one workspace's blocking neither leaks into nor strips another's on the shared sample. Metric definitions cannot use a blocked column. **PostgreSQL address pinning:** a name is resolved once, every address must pass the allowlist, and the driver is given exactly those addresses (`hostaddr`, with `host` kept for TLS), which closes DNS rebinding; a listed name that does not resolve cannot be pinned and is refused; the allowlist is re-checked each time a saved connection is used, so tightening `ALLOWED_DB_HOSTS` takes effect at once. **Frontend:** login and registration screen (repeat password, rules stated, server reasons shown, no sign-up link when closed), account page (change password, log out), the top bar shows who is logged in, an expired or ended session returns to login with the reason, and the app is mounted per user so one person's loaded data can never remain on screen for the next; Schema page checkboxes to block a column or a whole table (optimistic, with rollback, and the preview is re-read only once the change is saved).
- **Verified:** 819 backend tests (new: 32 blocked columns, 6 address pinning against the real PostgreSQL server including a name only the pinned address can reach, 8 host-policy, 25 password and limiter, 51 accounts, 44 for rate limits, headers and log redaction) and 261 frontend tests. Mutation check: the cache-key tests fail when the key change is removed. Live in a real browser with the real model: registering (mismatch and rule errors), blocking `customers.email`, a question asking for email addresses (the model answered that the schema has no email column), the model limit slowing the third question with a plain message, lockout after three wrong passwords, a second person seeing an empty history, an unblocked `email` column and their own preview, password change, and a phone-width login with no overflow.
- **Fixed during review:** (1) the login token kept an in-memory copy that came back after being removed from storage (logging out in another tab), now storage is the source of truth and memory is only the fallback when storage fails; (2) the blocked-column checkbox only ticked after the server replied, so it felt dead (now optimistic with rollback, and the preview refresh waits for the save); (3) a doubled backslash in the host check collapsed into an invalid escape while editing; (4) the login card stretched to the page height; (5) pinning had to keep uvicorn's five-field access-log arguments intact, so redaction cleans the tuple instead of flattening it.
- **Known limits:** limiters and lockouts are in memory in one process (several processes each count separately, and a restart clears them); the client address is the direct peer, so behind a reverse proxy every login attempt looks like one address unless the proxy is made trusted (not built); there is no account deletion or password reset by email; data created before accounts existed (under the old random browser id) is not carried over; sessions are bearer tokens in `localStorage`, so a cross-site scripting hole would expose them (the UI renders everything as text nodes, and the CSP above covers the API only); the pinned address is kept for the life of a saved connection's pooled engine, so a database whose address legitimately changes needs a Refresh or restart; the relationship diagram still draws blocked columns (it shows the full schema so blocking can be managed); an answer and its written summary each count against the model limit; `/api/database/test` can still be used to probe allowed hosts at the general rate and still needs its own tighter limit, a per-workspace connection cap, and views are not listed (all three carried into 10c).

#### 10b: Speed and evaluation `[x]`
- Cut chat latency (see Stage 5 limits): run the ambiguity check and SQL generation concurrently, or skip the check for clearly specific questions.
- Add "Compare it with 2024"-style comparison questions (month-by-month side by side) to the evaluation set.
- Evaluation suite from README section 15 (accuracy, join correctness, unsafe-rejection rate).
- **Built:** **Overlapped chat** (`AMBIGUITY_PARALLEL`, on by default): the first SQL-generation call starts in a worker thread while the ambiguity check runs, and `run_question` takes that call as its first reply, so a clear question waits for the slower of the two instead of both. If the question is vague, the answer to the user is the clarification straight away; the abandoned generation is never validated or executed and its failure is ignored. Everything else is unchanged (the correction loop, an answered clarification, the join ambiguity, the check switched off). Not built: skipping the check for questions that look specific, because that trades answer quality for speed whereas the overlap does not. **Evaluation suite** (`backend/evaluation/`, run with `python scripts/evaluate.py`): 61 questions in 14 categories (the README's table, plus business definitions, comparisons and follow-up conversations), each with a reference SQL run on the same data, so "correct" means the rows match, not that the SQL ran. Questions go straight through the chat workflow on a private copy of the sample database and a small uploaded CSV in a temporary folder, three conversations at a time, and every case is checked for whether any data changed. It reports every metric in README section 15: schema linking (before any model call), table and column identification, join correctness, SQL execution accuracy and first-try validation, result correctness (lenient: extra or reordered columns allowed, wrong or missing rows not; and exact), visualization suitability, ambiguity detection (recall, false alarms, precision, F1), unsafe-request safety, invalid-schema handling, and timing. Output is `docs/evaluation_report.md` (with each failure's question, SQL and reference) and `docs/evaluation_results.json`; the command exits with an error if any request changed data or revealed blocked values.
- **Measured (live `gpt-5-nano`):** overlapped chat took 4.5 s per question on average against 6.3 s one after the other (about 28% less; 6 questions, 2 alternating rounds, so noisy: a single model call varies from 3 to 13 s). It saves nothing on a question that turns out vague, where the generation is wasted. **Evaluation, three full runs of the final code: 60, 60 and 59 of 61 (98.4%, 98.4%, 96.7%).** Over those runs: ambiguity recall 100%, data unchanged 100%, blocked values never leaked, no unsafe request executed, questions about data that does not exist handled without inventing it 100%, visualization suitability 100%, SQL execution accuracy 96 to 100%, schema linking 100%, mean time per question 5.2 to 6.4 s. Before the prompt changes below the first run scored 53 of 57.
- **Found by the evaluation and fixed (product):** (1) asked to compare 2024 with 2025 "month by month, side by side", the model grouped by year-month, so each row had a value in only one year's column; the cause was partly the SQLite note itself, which taught `strftime('%Y-%m', ...)` for "a month". Now the notes distinguish year-month from month-of-year, and a worked period-over-period query is given in both dialects (both examples are executed in tests, on SQLite and on real PostgreSQL), plus a rule to give each period its own column. (2) asked for a customer's phone number, the model returned `NULL AS phone_number`, a fabricated empty column; a new rule forbids placeholders and asks it to say what is missing. Because both fixes were written looking at questions in the set, four held-out questions in different wording were added (customer sign-ups month by month, payments per method per year, date of birth, order discount) and all four pass; the questions the rules were written from are no longer a fair test of generalisation.
- **Found by the evaluation and fixed (the evaluation itself):** (1) the column-identification score treated `o.status AS status` as an invented alias and scored a correct column as missing (75% became 100%); (2) one question ("which customer placed the most orders") has no single answer because two customers tie at 17, which my own probe had missed by grouping on names; a tie check now covers every top-N reference (reverse the tie-break both ways and require the same rows) and the question was replaced; (3) for a single-year monthly question the labels `2025-03` and `03` are both right, so a case can list alternative accepted answers; (4) two questions were duplicated, which a uniqueness test now forbids. The shared test double for the model now hands each call the reply that fits its kind, since two calls are in flight at once.
- **Known limits:** the model is not deterministic: one or two questions out of 61 flip between runs, and the two that failed in the last run were clear questions answered with a meaningless clarification ("Please provide data to compute the count"), which a prompt change cannot reliably remove; join correctness is 85 to 92% because the model sometimes joins a table it does not need (the revenue question joins `payments`, which gives the right number here only because every completed order has a payment), an open weakness the suite now measures; the unsafe rejection rate (33 to 83% across runs) only counts outright refusals, since the model often answers an unsafe request with a harmless SELECT, which is safe and is scored as such; the suite covers SQLite and one uploaded file, not PostgreSQL (the live PostgreSQL tests from Stage 8 remain the check there); the latency figure is a small sample; with `AMBIGUITY_PARALLEL` a vague question costs one wasted model call.

#### 10c: Documentation and database limits `[x]` (MySQL left out)
- MySQL support (dialect and read-only handling). **Decision: left out of this version.** There was no MySQL or MariaDB server on the development machine and no Docker, so the read-only guarantees could not be verified the way PostgreSQL's were (against a real server, including an account that can write). Shipping a connector whose safety is untested was not acceptable for a feature whose whole point is safe read-only access, and a mock-only version would have looked supported without being so. The official MySQL 8.4.3 server was downloaded to try it; running it was declined, so no MySQL code was written and the downloaded files were deleted. The README says plainly that MySQL is not supported.
